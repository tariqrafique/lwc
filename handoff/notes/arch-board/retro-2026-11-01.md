## AB-R001: Fix A, `SourceLocation.start/end: Option<u32>`  (REWORK)

**1. Symptom / first wrong state.**
CSS errors have no byte offsets: PostCSS `CssSyntaxError` goes through `getLocationFromObject`, which yields `{line, column}` only. To carry that, `lwc-shared/src/lib.rs:58-59` made the *shared* `SourceLocation` offsets optional. That one type is used in three places:
- the template IR (`lwc-shared/src/template_ir.rs` re-uses it; Default at `template_ir.rs:13-16` = `start: Some(0), end: Some(0)`)
- every diagnostic (`CompilerDiagnostic.location`, lib.rs:38)
- `DiagnosticOrigin` (lib.rs:509-512)

The first wrong state is the type change itself. After it:
- Every IR node can now represent an offset-less location, which upstream never produces.
- `SourceLocation::span()` (lib.rs:66-70) panics on `None`. That is a guard placed downstream of the bad state, and the doc comment (lib.rs:50-51, 63-65) claims a narrower invariant than the code keeps.
- `lwc-style/src/lib.rs:78` sets `start: None, end: None` for *every* CSS error, not only source-map-remapped ones, contradicting the lib.rs:50-51 comment.

Knock-on placeholders that the lossy type invites:
- `lwc-js/src/parse.rs:74` fakes a zero-width `SourceLocation` with `start = end = Babel index`, which napi then un-fakes in `babel_position` (`lwc-compiler-napi/src/lib.rs:238-240`).
- `lwc-ssr/src/compile_js/dynamic_imports.rs:78` builds `SourceLocation { start_line, start_column, ..Default::default() }`. That is a fake end 1:1 and offsets Some(0).
- napi `css_location` (lib.rs:232-234) strips start/length again.

There are now three per-origin location rewrites, in three crates.

**2. Layer / kind.** shared-infra. lossy-model, plus duplicated-source-of-truth: the location is reshaped per origin at the seam as well as at the producer.

**3. Upstream owner.**
- The IR location is always complete. `/workspace/lwc/packages/@lwc/template-compiler/src/shared/types.ts:37-44`: `SourceLocation {startLine, startColumn, endLine, endColumn, start, end}`, all required.
- `parser/ast.ts:192-201` `sourceLocation()` always sets offsets from parse5.
- Optionality lives only at the diagnostic level: `/workspace/lwc/packages/@lwc/errors/src/shared/types.ts:28-33` `Location {line, column, start?, length?}`.
- Producers convert at their own boundary:
  - template: `parser/parser.ts:35-50` `normalizeLocation`
  - CSS and Babel: `errors/src/compiler/utils.ts:135-147` `getLocationFromObject`, which takes `obj.loc` for a Babel Position or `{line, column, start, length}`.

**4. Right fix level / what to delete.** Keep the two types separate, as upstream does.
- `SourceLocation` (IR) goes back to `start: u32, end: u32`. Delete `span()` and its panic; callers read the fields.
- Delete `impl Default for SourceLocation` outside `#[cfg(test)]`.
- `CompilerDiagnostic.location` and `DiagnosticOrigin.location` become `Option<DiagnosticLocation>`. That is the existing @lwc/errors `Location` mirror at lib.rs:492-497. If Babel's `Position` must survive the seam, add `index: Option<u32>` to it.
- Each producer converts once, at its upstream point:
  - template: `From<SourceLocation>` = `normalizeLocation`
  - lwc-style: `{line, column, start: None, length: None}`
  - lwc-js Babel parse: `{line, column, index}`
- Delete:
  - napi `css_location` and `babel_position` (lib.rs:232-240) and the origin branches at lib.rs:252, 266-267
  - the fake zero-width location in `lwc-js/src/parse.rs:74`
  - the `..Default::default()` placeholder in `lwc-ssr/src/compile_js/dynamic_imports.rs:78`, which must build a real `DiagnosticLocation` from its line/column
- Then fix the doc comment at lib.rs:49-51.

**5. Verdict: REWORK.** Required shape: IR `SourceLocation` has no `Option` fields, and diagnostics carry `Option<DiagnosticLocation>` built by the producer.

**6. Structural guard.**
- The type is the guard: the IR location has no `Option` and no non-test `Default`, so a fake or absent offset cannot be represented.
- Add a shim-gate style lint that fails on `SourceLocation {` … `..Default::default()` under `crates/*/src` outside `#[cfg(test)]`.
- The napi `error_result` must not branch on `Origin` for location shape. Add a napi test asserting `to_js_diagnostic(d).location == d.location.map(Into::into)` for every origin.

## AB-R002: Fix B, PostCSS `syntax_check` pre-pass  (REWORK)

**1. Symptom / first wrong state.**
`lwc-style/src/lib.rs:118-123` (`transform_with_config`) runs `syntax_check::check(src)` and then `parser::parse(src)`. The input is tokenized and parsed twice, by two different grammars:
- `syntax_check.rs` (393 lines; header at 1-12) is a port of PostCSS 8.5 `tokenize.js` + `parser.js` control flow over UTF-16 offsets. It decides only whether and where PostCSS would throw, and builds no nodes.
- `parser.rs` is a cssparser (CSS Syntax §5) tree builder that auto-closes at EOF where PostCSS throws.

The first wrong state is building the tree with a parser whose acceptance set differs from PostCSS's, then patching the gap with a second pass.

Residue of the duplicated rule set:
- `parser.rs:101` still raises its own `Unknown word {text}`. notes/postcss-rust/07-error-parity.md admits nothing proves this is unreachable.
- `parser.rs:15` has an `"Unknown parse error"` fallback.
- `parser.rs:62-66` re-encodes, in a comment, which bracket cases `syntax_check` already rejected.
- Positions come from two models: UTF-16 `Input#fromOffset` in syntax_check versus cssparser line/column in parser.rs.
- `syntax_check` is `pub mod` (lib.rs:13), so it is a second public entry point.

**2. Layer / kind.** parser. duplicated-source-of-truth (two grammars decide acceptance), plus a dead fallback (`parser.rs:15`, `parser.rs:101`).

**3. Upstream owner.**
- `/workspace/lwc/packages/@lwc/style-compiler/src/transform.ts:78-94`: a single `postcss(plugins).process(src, {from: id}).sync()`. A `CssSyntaxError` is thrown from inside the one parser that builds the tree.
- `/workspace/lwc/node_modules/postcss/lib/parse.js:7-12` → `parser.js`. `endFile()` → `unclosedBlock` at :334-335/:573; `unknownWord` at :594; `unexpectedClose` at :586; `checkMissedSemicolon` at :122. The tokenizer is created at :192.

**4. Right fix level / what to delete.**
- There must be one parser, and it builds the lossless tree. `syntax_check.rs` already ports the PostCSS tokenizer and parser control flow, so extend it to build the `ast` nodes with raws, as `parser.js` does.
- Then delete the cssparser-based `parser.rs`, including its `Unknown word` (:101) and `Unknown parse error` (:15) paths.
- Alternative: keep the cssparser tree builder but make it consume the PostCSS token stream, so there is still exactly one tokenizer and one acceptance decision.
- Either way: `pub fn parse(src) -> Result<Root, StyleError>` is the only entry, `syntax_check` is no longer a public module, and `transform_with_config` calls one function.

**5. Verdict: REWORK.** Required shape: a single-pass PostCSS-faithful parser that both builds the tree and raises `CssSyntaxError`. Delete the separate `check()` pass and the parser.rs error fallbacks.

**6. Structural guard.**
- Module structure is the guard: one `parse` entry, no `pub mod syntax_check`, and no `StyleError::syntax` constructor reachable outside the parser module.
- Add a regression corpus test: every `tests/parse-errors/*` and every accepted CSS fixture goes through the one parser, and `transform_with_config` must not call any other syntax function. An `rg` check in board.sh for `syntax_check::check` would catch reintroduction.

## AB-R003: Fix C, AggregateError shaping in lwc-compiler-napi  (REWORK)

**1. Symptom / first wrong state.**
The `CompilerAggregateError` and `CompilerError` shape is built in four places and then re-shaped at the seam:
- `lwc-shared/src/lib.rs:449-465` `CompileError::aggregate`. Its message is the header plus every sub-message, the old "Phase A" shape. Used by `lwc-js/src/lib.rs:25` and `lwc-js/src/transforms/mod.rs:42`.
- `lwc-style/src/lib.rs:43-63` builds its own aggregate with `CSS_AGGREGATE_MESSAGE` (:66).
- `lwc-compiler/src/lib.rs:91-101` builds the template aggregate (message "", no filename).
- `lwc-compiler-napi/src/lib.rs:242-290` `error_result` then rewrites them:
  - it replaces message, code and filename via `aggregate::surface` (`aggregate.rs:25-31`)
  - it puts back the style and template messages that `surface` just discarded (lib.rs:248-257)
  - it re-derives each entry's `level`/`url` (`aggregate.rs:35-47`) and the single-error `level`/`url` from a re-derived file-kind `Origin` (`single_error.rs:28-58`, "Mirrors `lwc_compiler::dispatch` routing")
  - it strips locations per origin (lib.rs:252, 266-267)

The aggregate is recognized by a string sniff, `name == "AggregateError" && !diagnostics.is_empty()` (`aggregate.rs:20-22`). The doc comment at aggregate.rs:18-19 ("lwc-style's CSS AggregateError carries no diagnostics") is stale: lwc-style now fills them (lwc-style/src/lib.rs:46).

Other leftovers:
- `AGGREGATE_EXACT_SHAPE` (aggregate.rs:14) is a migration switch left at `true`. Its `false` branch (aggregate.rs:29) is a dead fallback.
- `error_urls.rs:4-12` is a generated second copy of the @lwc/errors url table, because lwc-shared has no complete error-info table.

The first wrong state is that `lwc_shared::CompileError` is a loose struct (`message, filename, diagnostics, name: Option<String>, line, column`; lib.rs:299-307) that cannot express `CompilerError` versus `CompilerAggregateError`. Every layer patches it instead.

**2. Layer / kind.** seam-napi. duplicated-source-of-truth; also missing-upstream-structure (no `CompilerError` / `CompilerAggregateError` / `normalizeToCompilerError` model) and shim-workaround (the Phase A/B switch).

**3. Upstream owner.**
- `/workspace/lwc/packages/@lwc/errors/src/compiler/utils.ts:15-81`: `CompilerError` with `from()`; `CompilerAggregateError` at :74-81.
- `/workspace/lwc/packages/@lwc/errors/src/compiler/errors.ts:48-68` `generateCompilerDiagnostic`, and `:128-158` `normalizeToCompilerError` (message `${error.name}: ${message}`, level and url from the fallback info).
- Each transformer shapes its own throw:
  - `/workspace/lwc/packages/@lwc/compiler/src/transformers/style.ts:44-61` (CSS_TRANSFORMER_ERROR; aggregate message 'Multiple CSS errors occurred during compilation.')
  - `transformers/template.ts:72-86` (`CompilerError.from`; aggregate with no message)
  - `transformers/javascript.ts:109-135` (JS_TRANSFORMER_ERROR / JS_TRANSFORMER_DECORATOR_ERROR sniff; 'Multiple errors occurred during compilation.')
- The napi seam has no upstream counterpart. It must only serialize.

**4. Right fix level / what to delete.**
- Port the @lwc/errors model into lwc-shared:
  - `enum CompileError { Compiler(CompilerError), Aggregate(CompilerAggregateError) }`
  - `CompilerError { code, message, filename, location: Option<DiagnosticLocation>, level, url }`
  - `CompilerAggregateError { message: String, errors: Vec<CompilerError> }`
  - `normalize_to_compiler_error(fallback_info, err, origin)` and `CompilerError::from(diagnostic)`
  - a complete `LwcErrorInfo` table that carries `url` (single source)
- Build errors in the lwc-compiler transformer facades (style, template, javascript) exactly as the three upstream transformers do. lwc-style returns raw `CssSyntaxError`s, and lwc-js returns diagnostics or Babel errors.
- napi maps the enum 1:1 to JS objects.
- Delete:
  - `lwc-compiler-napi/src/aggregate.rs` (the `surface`, `AGGREGATE_EXACT_SHAPE` and `is_compiler_aggregate` logic, and the per-entry url/level derivation), `single_error.rs`, and `error_urls.rs`
  - the `Origin` branches in napi `error_result`
  - `CompileError::aggregate` in lwc-shared
  - the aggregate construction in lwc-style lib.rs:43-63, which moves to the lwc-compiler style facade
- `resolve_like_node` (Babel's cwd-resolved filename) belongs to the JS transformer facade, which models Babel's `filename` resolution, not the seam.
- The shipped-fixture tests in aggregate.rs and single_error.rs are good evidence. Move them to lwc-compiler as output-level tests.

**5. Verdict: REWORK.** Required shape: typed CompilerError and CompilerAggregateError in lwc-shared, built once per transformer in lwc-compiler, with no shaping in napi.

**6. Structural guard.**
- With the enum, an "aggregate" can no longer be detected by string-matching `name`.
- lwc-compiler-napi must not depend on any error-info table: a board.sh `rg` check fails if napi/src contains `level_url`, `error_url`, `Origin::` or `AGGREGATE_`.
- A napi test asserts `JsCompileError == serialize(lwc_compiler::dispatch(..).unwrap_err())` field by field, with no origin input.

## AB-R004: Fix D, template codegen shouldFlatten / fragment (`fr`)  (APPROVE)

**2. Layer / kind.** codegen. port-fidelity-gap, now closed.

- `index.ts:215-246` `transformScopedSlotFragment`; `codegen.ts:294-301` `genFragment(key, children, stable=false)` → `[key, children, 0]`

**4. Fix level: correct.**
- `codegen/mod.rs:181-188` `should_flatten` is a clause-by-clause port of helpers.ts:47-64: for-block, light-DOM `<slot>` gated on `USE_FRAGMENTS_FOR_LIGHT_DOM_SLOTS`, and recursive `if:*`.

## AB-R005: Fix E, deletion of SSR `ir_compat`  (APPROVE)

  - masking and unmasking complex `for:each`
  - `mark_valueless_attrs`, `lift_quoted_complex` and `drop_errored_expr_nodes`
  - a parse5-1058 root filter
  - a mutable `root.clone()`
- The first wrong state was in lwc-template's parser. Root causes are listed per id in notes/lwc-ssr-rust/template-ir-contracts.md.

**2. Layer / kind.** ir-model. shim-workaround (now removed). The fix moved each correction to the owning layer.

**3. Upstream owner.**

- `ir_compat.rs` is removed in 7b3cdca.
- The same commit migrates the callers: the lwc-ssr/src/lib.rs hunk deletes every `SHIM(...)` call site, `root_has_preserve_comments` and `root.clone()`. The compile_template/mod.rs `mod ir_compat` declaration goes too.
